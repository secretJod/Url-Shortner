# scripts/

## `seed-demo-data.sql` — demo/local seed data

**What it is:** a plain SQL script that inserts a small set of realistic-looking
demo short links (pointing at real public sites like github.com and
wikipedia.org) plus a randomized, non-uniform spread of click-analytics rows
over the days each link has existed. It exists purely so a freshly created
dev or GitHub Codespaces instance has something to look at — a populated
dashboard, stats pages, and a top-links leaderboard — instead of an empty
database.

**This is demo/seed data, not real traffic.** Every row it inserts is
synthetic, generated by this script. It does not represent, simulate, or
claim to be real user activity, and there is no production deployment of
this project serving real users today. See the comment block at the top of
`seed-demo-data.sql` for the full detail.

**This is NOT how to seed a production database.** It is a dev convenience
script, not referenced by `docker-compose.yml`, CI, or the deploy workflow —
nothing runs it automatically, and it should never be run against a
database holding real user data.

### Why SQL instead of a Go program

The backend's only database access path is the generated Prisma client
(`backend/internal/db`), which is gitignored and only exists after running
`prisma generate` — a step that needs network access to download Prisma's
query-engine binary, and is normally done inside the Docker build. A plain
SQL script avoids that dependency entirely: it runs with nothing more than
`psql` against a reachable database, and can be read line-by-line against
`backend/prisma/schema.prisma`'s column names before anyone trusts it. The
trade-off is that it bypasses the application's own validation (URL format,
custom-alias character rules) — acceptable here because the content is
fixed and hand-reviewed, not user input.

### How to run it

Against the local Docker Compose stack:

```bash
docker compose exec -T postgres \
  psql -U urlshortener -d urlshortener < scripts/seed-demo-data.sql
```

Against any other reachable Postgres (e.g. inside a Codespace, where
`DATABASE_URL` is already set):

```bash
psql "$DATABASE_URL" -f scripts/seed-demo-data.sql
```

Run it *after* the schema exists (i.e. after the `migrate` service / `prisma
db push` has already applied `schema.prisma`).

### Safety / idempotency

- It checks whether its own demo short codes already exist and exits
  without inserting anything if so — safe to run more than once.
- It only ever inserts its own rows; it never modifies or deletes existing
  `users`, `links`, or `click_events` rows.
- It bumps the `links`/`click_events` ID sequences past what it inserts, so
  IDs the running app mints afterward never collide with seeded rows.
- All seeded links are anonymous (`user_id = NULL`) — an already-supported
  state in this app — so no fake user accounts, passwords, or API keys are
  created.
- Seeded short codes (`gh-mirror`, `wiki-ref`, `py-docs`, `hn-feed`,
  `nyt-world`, `so-faq`, `reddit-aww`, `mdn-js`) are custom-alias-style
  strings containing `-`, which the app's own counter-based code generator
  (base62, `0-9a-zA-Z` only — see `backend/internal/shortcode/base62.go`)
  can never produce, so they can't collide with organically-created codes
  either.

### Verification performed

This script was **not** run against this project's actual Prisma-migrated
schema (doing so would require bringing up the real `docker compose` stack,
which was out of scope for producing this script). Instead, it was verified
end-to-end against a disposable `postgres:16-alpine` container, using tables
hand-created to match `backend/prisma/schema.prisma`'s mapped column names
and types exactly (`short_code`, `long_url`, `user_id`, `custom_alias`,
`expires_at`, `password_hash`, `created_at`, `device_type`, `ip_hash`, etc.):

- First run: executed cleanly, inserted **8 links** and **2,709 click
  events**.
- Second run against the same database: detected the existing demo short
  codes and exited without inserting anything (confirms idempotency).
- Spot-checked afterward: all 8 links present with distinct creation dates
  over the last 2–28 days; click counts per link ranged from 31 to 776
  (reflecting each link's configured "popularity" and the number of days
  it had existed); device-type split was roughly 55% desktop / 38% mobile /
  6% tablet; countries and referrers were spread across the configured
  pools with no single value dominating.

Because this was verified against hand-built tables mirroring the schema
rather than a real `prisma db push` output, there remains a small residual
unknown: whether Prisma's actual generated DDL (exact type mappings,
constraint names, etc.) introduces any difference this script doesn't
account for. The column names, types, and constraints were cross-checked by
eye against `schema.prisma` and believed accurate, but this has not been
confirmed against a live `prisma db push`'d database.
