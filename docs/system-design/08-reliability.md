# 08 — Reliability

## CURRENT STATE — Failure mode analysis (evidence-based)

| Failure | Current behavior | Evidence | Assessment |
|---|---|---|---|
| Redis unreachable | Rate limiter **fails open** (all requests allowed, unlimited) | `middleware/ratelimit.go:52-56`, explicit comment "Fail open: a Redis hiccup shouldn't take down the whole API" | Reasonable availability-over-strictness trade-off for a rate limiter specifically, but means **rate limiting silently disappears** during a Redis outage with no alert — an operator has no signal this happened (no metric/log distinguishing "fail open due to error" from "normal allow") |
| Redis unreachable, redirect path | Cache-miss path falls through to Postgres — redirects keep working, just slower | `handlers/redirect.go:39-43` — comment: "Redis itself errored ... log and fall through to Postgres rather than failing the request outright" (but the log never actually happens, see `09-observability.md`) | Graceful degradation is architecturally present but **not observable** — no metric increments to distinguish this fallback path from a normal cache miss |
| Redis unreachable, shorten path | **Hard failure** — `resolveShortCode` (`shorten.go:105-125`) calls `h.Redis.NextID` or `h.Redis.ReserveAlias`, both of which propagate the Redis error straight to a `500` | `shorten.go:120-123` | **Single point of failure**: all URL creation stops if Redis is down, with no fallback ID-generation strategy (e.g. a Postgres sequence fallback) |
| Postgres unreachable | Redirects on cache hit still work; cache misses `500`; all writes (`shorten`, `api/keys`) `500` | `redirect.go:46-54`, `handlers/apikeys.go:51-52` | Expected given Postgres is the system of record; no circuit breaker/backoff, each request independently retries the DB connection attempt per Prisma's own internal behavior — not evidenced further in this read-only pass |
| Health check while Postgres is down | **Reports healthy** — `/health` only pings Redis | `handlers/health.go:19-37` — no Postgres check anywhere in the handler | **Confirmed reliability gap**: an orchestrator using `/health` for readiness/liveness would keep routing traffic to an instance whose writes are entirely broken |
| Analytics worker crash | Worker is a goroutine inside the same process as the API (`worker.Start(ctx)` called from `main.go:46`, launched with `go w.run(ctx)`) — a panic in `w.run` is **not recovered** (no `recover()` in `worker.go`), which would crash the entire process, taking the API down with it | `worker/worker.go` (no `defer recover()` found), `main.go:45-46` | **HIGH-impact evidenced coupling**: an unhandled panic in analytics processing (e.g. a malformed stream payload triggering a nil dereference somewhere not yet hit by tests) kills the whole API, not just analytics. Contrast with the *handler* path, which is protected by Fiber's `recover.New()` middleware (`main.go:53`) — the worker goroutine has no equivalent protection since it isn't inside Fiber's request lifecycle. |
| Graceful shutdown | Implemented for the HTTP server: SIGINT/SIGTERM → `cancel()` (stops the worker's context) → `app.Shutdown()` (Fiber lets in-flight requests finish) | `main.go:134-142` | Correct pattern; **not verified whether `app.Shutdown()` is awaited before process exit** — `main()` returns immediately after starting the goroutine that calls `Shutdown()`, and the `app.Listen()` call below it returns once `Shutdown()` unblocks it, so in practice the main goroutine does block on `Listen()` returning — this is **correct**, confirmed by re-reading `main.go:135-147` end to end. No finding here, listed for completeness. |
| Retries / backoff on transient errors | **None** anywhere in the reviewed code for Postgres or Redis calls (aside from the analytics worker's blanket `time.Sleep(1s)` on any `ReadClickEvents` error, `worker.go:69`) | `worker.go:67-70` | A single generic 1-second sleep-and-retry for *any* stream-read error (including permanent ones, e.g. misconfiguration) is a blunt instrument — no exponential backoff, no distinction between transient and permanent failure classes |
| Idempotency | `POST /api/shorten` is not idempotent (no idempotency key) — retried requests create duplicate links | `shorten.go` (no dedup logic) | Low severity as noted in `04-api-design.md`; listed here for completeness under CLAUDE.md §16 |
| Backups / restore / DR | **No backup strategy found anywhere in the repo** — no `pg_dump` cron, no volume snapshot automation, no documented restore procedure. Data lives entirely in the `pg_data` named Docker volume with no offsite copy. | `docker-compose.yml` (only a bare named volume, no backup service/sidecar) | Confirmed absence, not merely unconfirmed — this is a real gap for any deployment beyond throwaway local dev |

## PROPOSED PRODUCTION STATE — Reliability fixes, ranked

1. **Add Postgres to `/health`**, and distinguish liveness ("is the process alive") from readiness ("can it serve traffic") — e.g. `/health/live` (always 200 if the process is up) vs `/health/ready` (checks both Redis and Postgres) — this is the highest-leverage, lowest-effort reliability fix available.
2. **Wrap the analytics worker's `run()` loop in a `recover()`** so a panic in click-event processing degrades analytics (acceptable, already fire-and-forget by design) instead of taking down the entire API process.
3. **Add a scheduled Postgres backup** (even a simple `pg_dump` cron container, or the managed provider's built-in backup feature if one of the free-tier managed Postgres options from `06-deployment.md` is chosen — Supabase/Neon both include automated backups on their free tiers, which would solve this at $0 cost by provider choice rather than custom tooling).
4. **Fallback ID generation strategy** if Redis is down (e.g. a Postgres sequence as a documented degraded-mode fallback) so URL creation doesn't have a hard dependency on Redis being up — or explicitly accept and document this coupling as a deliberate trade-off if the added complexity isn't justified (Phase 2 decision).
5. **Horizontally scale the analytics worker** as its own deployable (see `02-high-level-design.md` proposed architecture) so a worker crash-loop cannot affect the API process, and multiple consumers in the existing `analytics-workers` consumer group can share load (the code already supports this — `ConsumerName` is just hardcoded to `"worker-1"` in `worker.New()`, trivially parameterizable).

## PROPOSED PRODUCTION STATE — Container-native process management (PM2 rejected)

**Status: PROPOSED — not approved, not implemented. See `adr/0006-containerized-operations-and-process-management.md` for the full decision record; this section covers the reliability-relevant content (crash-restart, liveness/readiness, graceful shutdown). See `06-deployment.md`'s "Fully containerized operations" section for the build/run lifecycle and showcase framing.**

The user asked whether PM2 should manage this project's processes. **Evidence-based answer: no.** PM2 is a Node.js process manager. This repo has no long-running Node process anywhere: the backend is a compiled Go binary (`backend/Dockerfile`, 3-stage build → Alpine runtime), and the frontend is a Vite-built static SPA with no runtime Node server (served by the Go binary via `app.Static`/`SendFile`, or proposed to be served by nginx per ADR-0005). Introducing PM2 here would mean installing a Node.js runtime into an image solely to supervise a binary that already handles its own lifecycle — added image size and attack surface for zero benefit, and a cargo-cult signal to anyone reviewing the repo.

The correct container-native mapping of PM2's responsibilities onto this stack:

| PM2 responsibility | Container-native equivalent | Status in this repo |
|---|---|---|
| Crash-restart a dead process | `restart: unless-stopped` (Compose) | **Already present** on all 5 services in `docker-compose.yml` |
| Liveness/readiness status (`pm2 status`) | Docker `healthcheck` | Present on `postgres` (`pg_isready`) and `redis` (`redis-cli ping`). **PROPOSED**: add to `api` (existing `/health` endpoint — see the gap noted above re: Postgres not yet included in that check), `prometheus` (`/-/healthy`), `grafana` (`/api/health`) — all endpoints the images/binary already expose |
| Graceful reload (`pm2 reload`) | SIGTERM handling in the process itself | **Already implemented** — `backend/cmd/api/main.go:134-141`: `signal.Notify` on SIGINT/SIGTERM → `cancel()` (stops the analytics worker's context) → `app.Shutdown()` (Fiber drains in-flight requests). Compose sends SIGTERM by default on `stop`/`down`, so this is already correctly wired, just not yet verified under a documented drill |
| Process supervision inside one unit | "One process per container" (industry norm) | **Already the shape of this repo** — each of the 5 services is a single foreground process in its own container; no in-container supervisor needed or proposed |

**Proposed step-up for orchestration maturity** (optional, not required for the base fix above): Docker Swarm (`docker stack deploy` against the same `docker-compose.yml`, minimal new config) or a lightweight Kubernetes (k3s/kind, stronger resume signal, more manifest work). Full trade-off discussion in `adr/0006-containerized-operations-and-process-management.md`.

This closes part of Reliability fix #1 above (readiness semantics) by proposing healthchecks on the three currently-unmonitored services, and formalizes that the crash-restart and graceful-shutdown mechanisms this project needs already exist — the gap is monitoring/liveness signaling, not a missing process manager.
